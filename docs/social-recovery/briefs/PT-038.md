## Interfaces and invariants

- Consumes `IProvider`, `IRecoveryClient`, `ISetupClient` and the builder, all typed from `sdk-interfaces/` and implemented by PT-035's doubles until the SDK lands. Wraps PT-035's cut-q-22 seam so screens never import it.
- Invariants: none listed. The done entries: the extension builds one client from a configuration naming one chain, the address book of the manager, the methods and the action, and a provider adapter whose four reads route through the extension's own provider, and it hands the client no signer and no storage; the signer facade signs typed data or raw bytes for a key the keystore holds, addressed by address and key type, and exposes no key export; with no rail configured every prepared call is sent from a key the signer holds, and the digest version the manager publishes through its domain is checked when the client is built, a disagreement refusing the client before anything is prepared; the table of the kit's audited actions with their publishers is the extension's own and is the only source of the action a screen offers or names.

## Shape and the facts of this codebase

- The provider: build an `ethers` provider through `getRpcProvider` of `src/ambire-common/src/services/provider/getRpcProvider.ts` from the network record the UI reads through `useNetworksControllerState`, for the one chain the configuration names. That provider may route through the light client (Helios), which is the "send may route through a light client and its prover" of D-370. The adapter implements `IProvider`'s four reads over it. Balance reads and gas estimates run on the same provider beside the adapter, exported by this lane for PT-039.
- The signer: the keystore and its signers live in the background (`KeystoreController.getSigner(addr, type)` in ambire-common, reached from the UI only by dispatch through `useBackgroundService`). The facade therefore signs by dispatching the extension's existing sign-message request flow (`SignMessageController`) for typed data and for raw bytes, addressed by the keystore's own handle of address and key type, and never holds a key in the UI. If that flow cannot sign for an arbitrary key the keystore holds, or cannot sign raw bytes, the implementer stops at that member, records exactly which background action is missing, and reports it; a new background action touches a shared file and is the owner's call. The facade exports no key export member.
- The client is built through the builder double of PT-035 against the doubles, and the module exports one `buildRecoveryClient(config)` and the configuration type, with the digest-version check inside it. A disagreement throws a typed refusal the account step renders as "update the wallet" (D-306, D-319).
- The audited-actions table and the two deployment descriptors of D-208 are plain `as const` data in this lane with placeholder addresses under cut-q-7.
- No React component; a hook that hands a screen the client is allowed and small.

## Test expectations

Jest, node environment, under `shared/client/__tests__/`, with the provider and the background dispatch mocked:

- the client builds from a configuration naming one chain and the address book, and the doubles receive no signer and no storage (assert the builder double was called with exactly the configuration, adapter and descriptor);

- the audited-actions table is the only source: a lookup by an address absent from the table yields the lane's explicit "unknown action" value.
