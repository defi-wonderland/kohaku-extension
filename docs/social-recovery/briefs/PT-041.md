## Outcome

`src/web/modules/social-recovery/shared/ceremony/` is the full tab every focus-sensitive ceremony runs in and the hosts that drive a method's four calls (enroll, test access, create claim, health check, D-372). Every enrollment row of D-305 and every checklist row of D-392 opens its ceremony through this module. A ceremony run in the action popup dies on focus loss, and a verdict folded into a skip reads a failed method as an untested one.

- Consumes `IMethodsOrchestrator` and `IRecoveryMethod` from `sdk-interfaces/`, implemented by PT-035's doubles, reached through the client layer where one exists (PT-038 is a later round; this lane may import the doubles' method implementations directly for the hosts and says so in its README, the one allowed exception until PT-038 lands, to be replaced by the client in PT-038's follow-up).
- Uses PT-036's chip vocabulary for the four verdicts.
- Invariants: none listed. The done entries: every ceremony that dies on focus loss runs in a full tab and never in the action popup, a hidden tab dispatches nothing to the background until it is shown again, and a hand-off to a phone reports its result when the tab returns; the extension calls the authenticator itself, `navigator.credentials.create` at enrollment and `navigator.credentials.get` at a claim, hands the result to the method, and reads the synced or device-bound kind from the ceremony's own flags; every test reports exactly one of four verdicts (passed, failed with its cause, unavailable with retry, not supported without one), and a ceremony the holder dismissed or the browser refused returns before the method runs as its own note.

## Shape and the facts of this codebase

- The route: the setup registered `WEB_ROUTES.socialRecoveryCeremony` (`social-recovery/ceremony`) under the module's route registry `src/web/modules/social-recovery/routes/SocialRecoveryRoutes.tsx`, itself mounted inside `TabOnlyRoute`, so any open from the popup redirects to `tab.html`. This task adds exactly one `<Route>` line in that registry for its screen; that is the one edit outside the lane folder and the brief records it.
- The tab screen takes its ceremony from the route's search params (method kind, call, and a request id the caller stored through PT-040's records or passes inline), runs the host, and returns the verdict to the caller through storage or a message the caller listens for; the design of that return channel is the implementer's, documented in the README, with the rule that a hidden tab dispatches nothing to the background (`document.visibilityState`).
- WebAuthn: the extension calls `navigator.credentials.create` and `.get` itself; the `rp.id` is the extension's own origin host; `authenticatorAttachment`, `transports` and the `BE`/`BS` flags of the authenticator data give the synced or device-bound kind; a `NotAllowedError` from the browser is the cancelled or refused note, read before the method runs; a high `s` in a P-256 signature is normalized (curve order `n`, `s > n/2` becomes `n - s`) before the method receives it.
- Hosts: one host per call (enroll, test access, create claim, health check), each rendering progress, abort and failure, each returning one of the four verdicts as a closed vocabulary.

## Test expectations

Jest under `shared/ceremony/__tests__/`, with `@jest-environment jsdom` where the DOM is needed and `navigator.credentials` mocked:

- each host maps a method result to exactly one of the four verdicts; a method that throws a cause yields "failed" with that cause, never "not tested"; a node or service that does not answer yields "unavailable" with retry; a method that cannot serve the document yields "not supported" with no retry;
- a `NotAllowedError` before the method runs yields the cancelled or refused note and the method's call count is zero;
- the synced or device-bound kind is read from the flags of a fabricated authenticator data, both ways;
- the high-`s` normalization: a signature with `s > n/2` is rewritten and one with `s <= n/2` is unchanged;
- the rp id is the extension's origin host and the committed hash is of the full origin string, never the bare id;
- the visibility rule: with `document.visibilityState === 'hidden'` no dispatch happens, and it resumes when visible.

Playwright: none in this task, since the passkey ceremony needs a real authenticator; the tester records what a manual run in a Chrome profile must cover (enroll, test access, create claim in the tab; dismiss; a hand-off) and the coordinator lists it as untested in the PR.
