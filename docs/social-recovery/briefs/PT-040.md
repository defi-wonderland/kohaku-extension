## Outcome

`src/web/modules/social-recovery/shared/records/` holds the extension's storage of every record D-310 names, in the extension's local storage and never in a background controller, since the worker restarts and clears its controllers. The SDK holds no session state (D-370), so the setup draft, the recovery session and the backup set live here and the SDK sees them only as arguments. A record kept in a worker controller or read as a bare zero loses the holder's progress or reads a default as a fact.

## Interfaces and invariants

- Storage: the extension's own helper `src/web/extension-services/background/webapi/storage.ts` (`get`, `set`, `remove` over `browser.storage.local`), whose `get` returns the default when the stored value is falsy. That is why no record is a bare boolean or zero: every record is an object carrying its value and `savedAt`. No controller, no `MainController` field, no background message.
- Record types: the setup draft is the setup draft record `sdk-interfaces/` declares (D-202); the path inside it is the same type PT-037 reads. The other records are this lane's own types: the inventory, the enrollments, the waiting period, the password-set flag (as an object, never a boolean), the recovery session (approvals, the predicted attempt id, the account address, the reason line), the countdown record (account address alone), the decrypted setup cache.
- The done entries: the six setup records live in local storage with their age and are wiped by save or start over while platform credentials survive; the recovery session holds the approvals and the predicted attempt id; exactly five events wipe both (the submission landing, the deadline passing, another attempt opening, the setup changing, the recoverer abandoning), and the wipe keeps one line of reason the death states render from; the session survives the submission as the countdown's record holding the account address alone; the decrypted setup stays as this device's cache after the recovery executes; a security stop wipes nothing (I-38); no record is a bare boolean or zero.

## Shape

One module exporting typed read, write, wipe and age functions per record, keyed by account address and chain where the record belongs to an account, with the storage helper injectable so tests run against an in-memory map. The five wipe events are one function taking the event as a closed vocabulary; it deletes the session and the approvals and writes the reason. Save and start-over are one function each for the setup records. No React, no hook in this lane; a hook belongs to the screen that needs it.

## Test expectations

Jest, node environment, under `shared/records/__tests__/`, against an in-memory storage double that mimics the helper's falsy-default rule:

- each of the six setup records round-trips with its `savedAt`, reports its age for a fixed `now`, and is gone after save and after start over, while a record standing in for platform credentials survives both;
- the recovery session round-trips with approvals and the predicted attempt id; each of the five events wipes both and leaves exactly the reason for that event; no sixth event exists in the vocabulary; a security-stop call, if the lane exposes one, wipes nothing;
- after the submission lands, the countdown record holds the account address alone and the session is gone;
- after execution, the decrypted setup cache stays;
- a stored `false` or `0` is impossible: writing the password-set flag stores an object, and reading an absent record returns the lane's explicit "absent" value, never `false` or `0` mistaken for a fact;
- no import from `@web/extension-services/background/controllers` or from `@ambire-common/controllers`.
