## Outcome

`src/web/modules/social-recovery/shared/display/` holds the value renderers and the status vocabulary of D-302 that every recovery surface calls, so each value type renders in exactly one form and each status word exists once. A second truncation or a second status word here appears everywhere at once.

## Design sections and deltas

- `design/ux.md` D-302 (vocabulary, display rules and naming: the value forms, the chip sets, the kit nouns' screen words, the four approval values, the two password names, the done screen's "controlled by" and "removed" exception).
- `design/ux-copy.md`: UXC-1 to UXC-7, UXC-9 (bans), UXC-10 and UXC-14 (the feature name, the approval value names and the kit nouns).
- `design/invariants.yaml` I-26 and I-41.

(2) Strings are registered in `en.json` under `socialRecovery.status` and `socialRecovery.display` by the setup task; this lane consumes those keys and adds none. A missing string is reported to the coordinator.

## Interfaces and invariants

- Interfaces: none from the SDK. The renderers take plain values (strings, bigints, dates) and the records `sdk-interfaces/` declares where a record is the natural input (the member list, the payment order).
- I-26: no status label claims the account is protected; the string `Protected` appears nowhere; no sentence says recovery protects the account.
- I-41: a resolved name beside a full address the reader is asked to check carries the caveat that the name can change hands and the full address is what to check; a name rendered alone for an address the reader acts on carries the same caveat.
- The done entries, one renderer per value type: short address as four and four hex digits; full address whole with no grouping; user-typed method name ellipsized past twenty four characters; hash as twelve and six; approval as twelve and eight; hidden value as sixteen dots beside a chip; member list as three then a count; payment order as symbol, amount and payee or the words "no payment"; deadline as a date and time in the reader's zone with the zone named and a countdown beside it. The chip sets are closed: method in setup (not started, in progress, tested, not tested, test failed, test unavailable, not supported, not yet active, saved, live), row in collection (not asked, waiting, declined, unanswered, complete, not needed, did not answer, stopped), attempt (recovery in progress, waiting, execution due, stopped, cancelled), recovery status (set up, not set up, with path locked, not active, cannot recover beside it). The module exports the screen word for every kit noun (recovery registry, recovery module, publisher, security stop, setup number, attempt number) and the two password names (extension password, recovery password).

## Shape

Pure functions first: every renderer is a function returning a string or a small plain structure, testable under the node environment, in `shared/display/render*.ts` or one `renderers.ts`. Status chips are one `as const` vocabulary per set plus a function mapping a chip to its i18n key. A thin React component (for example the hidden value with its chip) may live in `shared/display/components/` but holds no rule; the rule lives in the function it calls. Strings come from `i18n.t('socialRecovery.status.*')` and `i18n.t('socialRecovery.display.*')`; the functions accept a `t` parameter or import the app's `i18n` so tests run under node without React. The deadline renderer takes `now` and the zone as parameters so tests are deterministic.
