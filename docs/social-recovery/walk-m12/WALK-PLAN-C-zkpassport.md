# M-12, the walk's part C: the zkPassport identity on Sepolia with a real passport and the ZKPassport app (run by the SDK owner)

You are the walker. You set up this repository on this machine, build the extension with a Sepolia deployment line, load it in a headed Chromium through Playwright on the operator's screen, drive the passport enrollment and the passport claim with the real ZKPassport app on the operator's phone against the real Sepolia contracts, and write a report. You never post anywhere, never push, never edit a source file. The operator (the person running you) scans every QR with the app on their phone, accepts or declines in the app, and presses every Sign in the wallet: you stop before each of those and ask them in chat, then continue when they say it is done. Keep every seed, password, key, address and RPC URL out of chat and out of the report: they go into files under `walk-m12/run/` (mode 600), which stay on this machine.

Part A of this walk ran the identity rows on the fake node and the scripted stacks (`report-walk-a-fake-node.md`); part B ran the Aadhaar identity for real on Sepolia (`WALK-PLAN-B-aadhaar.md`, `report-walk-b-aadhaar.md`, `notes-walk-b-aadhaar.txt`). Read all three first: they show the screens, the strings, the driver bodies and the findings already known. Part C is the same walk for the passport: the ZKPassport app proves on the phone, the extension's ceremony tab shows the request as a QR and follows the phone's events through the bridge, the access test at enrollment is judged by the deployed zkPassport method's verify view (a chain read), the setup is saved on Sepolia, the claim at recovery goes through the phone again and is submitted on Sepolia.

## Facts you need

- The request is made in dev mode (`zkPassportTestnetTree: true` on the deployment line), so the app proves against zkPassport's testnet certificate tree, the one Sepolia's root registry accepts; the testnet tree holds every real certificate, so a real passport works. The SDK refuses mock proofs and sends `devMode` false to the verifier itself; only the request is in dev mode.
- The SDK's zkPassport method reads the enrollment material from the app's `onResult` payload; the proofs of a claim come from the same request; a decline in the app reads as refused; an error as failed with retry; a lost bridge connection before any proof as unreachable with retry; Cancel in the tab as cancelled (the stopped note).
- The deployment line fields for the passport: `methodZkpassport` (the deployed zkPassport method), `zkPassportDomain` and `zkPassportScope` (the app shows the domain as the requesting service; the scope keys the scoped nullifier; use the values the deployed method expects, which the operator gives you), `zkPassportTestnetTree: true`. Both of `zkPassportDomain` and `zkPassportScope` must be present together.
- The SDK package `@kohaku-eth/social-recovery` is unpublished: the build needs it packed from a local checkout of `defi-wonderland/kohaku` at `wonderland/dev` 08480f5 (the operator has that checkout; `docs/social-recovery/README.md` names the steps).
- The timings of part B for comparison: the setup save landed about 15 s after Sign; the submission and the execution each in one block; the 5-minute wait (the build's `SOCIAL_RECOVERY_WAIT_FLOOR_MINUTES=5`).

## Setup (do all of it yourself; ask the operator only for the five values named in the prompt)

1. In this checkout (branch `walk/m12-b`): `git submodule update --init src/ambire-common`; `yarn install` (plain: `--frozen-lockfile` never passes on this repository; the lockfile already carries `@zkpassport/sdk` 0.17.1 and `@anon-aadhaar/core` 2.4.3).
2. The SDK package: in the operator's kohaku checkout at 08480f5, `pnpm install --filter @kohaku-eth/social-recovery...`, `pnpm --filter @kohaku-eth/social-recovery build`, then `pnpm pack` in `packages/social-recovery`; extract the tarball into this checkout's `node_modules/@kohaku-eth/social-recovery` (replace the placeholder directory; a real directory, not a symlink; `tar -xzf <tgz> -C node_modules/@kohaku-eth/social-recovery --strip-components=1`). Check `node_modules/@kohaku-eth/social-recovery/dist/recovery-methods.js` exists.
3. Playwright: `npm install playwright-core@1.5x` in a scratch folder outside the repository and `npx playwright install chromium` there; set `WALK_PLAYWRIGHT` to that `node_modules/playwright-core` and `WALK_CHROMIUM` to the installed Chromium binary (on macOS `~/Library/Caches/ms-playwright/chromium-<n>/chrome-mac/Chromium.app/Contents/MacOS/Chromium`; `headless: false` plus `WALK_HEADED=1` shows the window).
4. `.env`: copy `.env-sample` to `.env`; set `SEPOLIA_RPC_URL` (the operator's, an archive-capable Sepolia endpoint; publicnode prunes history and fails log reads), `RPC_PROVIDER=rpc`, `SOCIAL_RECOVERY_WAIT_FLOOR_MINUTES=5`, and `SOCIAL_RECOVERY_SEPOLIA_DEPLOYMENT='<one JSON line>'` with: `manager`, `methodEcdsa`, `methodPasskey`, `action` (the 2026-10-20 Sepolia deployment: policyManager, ecdsaMethod, passkeyMethod, recoveryAction), `methodZkpassport` (zkPassportMethod of the same deployment), `zkPassportDomain`, `zkPassportScope`, `zkPassportTestnetTree: true`, `deployedAt: 11923225`, `digestVersion: "1"`, `managerVersion: "1.0.0"`, `auditedActions: [{ "action": <the action>, "publisher": "ethereumFoundation" }]`, `explorerUrl: "https://sepolia.etherscan.io"`. No Aadhaar fields unless the operator wants the Aadhaar flow too (then `methodAadhaar` the test-only Aadhaar method, `aadhaarNullifierSeed` any decimal, `aadhaarCertificate` the contents of `walk-m12/testCertificate.pem` with `\n` escapes, and `gen-test-qr.js` makes the test QRs). The parser refuses unknown fields and a half pair; the shape is in `src/web/modules/social-recovery/shared/client/deployments.ts`.
5. Build: `yarn build:web:webkit > walk-m12/run/build.log 2>&1` (two to three minutes; the output `build/webkit-prod`). Do not run `yarn test`, tsc or lint.
6. Credentials: write the operator's guardian address (any address they control, or a throwaway) as `GUARDIAN_ADDRESS=` into `walk-m12/run/walk-credentials.env` (mode 600) and set `WALK_CREDS` to that file for `post.js` and `drivers/bp.js`; the wallet files `walk-m12/run/wallet-1.env` and `wallet-2.env` are written by `drivers/create-wallet.body` (adjust its output path to `run/`).

## The daemon

`walk-m12/daemon.js` opens one persistent Chromium profile with the build loaded and serves a command port: `WALK_HEADED=1 WALK_BUILD=<repo>/build/webkit-prod WALK_PROFILE=<repo>/docs/social-recovery/walk-m12/run/profile-1 WALK_PORT=9483 WALK_ARGS='--screen-info={1920x1200}' nohup node walk-m12/daemon.js > walk-m12/run/d-1.log 2>&1 &` (detached, so it survives your pauses); the same with `profile-2`, port 9484, `d-2.log`. A command is an async function body over `S` (`S.ctx` the context, `S.page`, `S.ext()` the extension pages, `S.shot(name)`, `S.text()`, `S.logs`/`S.net`/`S.swlogs`), posted with `WALK_PORT=9483 zsh walk-m12/r.sh < body` or `node walk-m12/drivers/bp.js <body>` (fills `{{NAME}}` from the credentials and wallet files in code and masks secrets in the answer). The drivers of part B: `create-wallet.body`, `open.body` (unlock and go to a route), `tab.body` and `upload.js` (the ceremony tab; for the passport the tab shows a QR instead of an upload: read `tab.body` for the capture loop and drop the upload act), `cut.js`, `logs.body`. The wallet needs exactly one Kohaku tab. Stop only the daemons you started, by pid (`kill -9` was needed), at the very end.

3.
